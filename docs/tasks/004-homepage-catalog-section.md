## Важная находка: WordPress кэширует список файлов-паттернов темы

При первом прогоне новые паттерны (category-tiles, product-highlights,
promo-banner) **не появлялись на странице вообще**, хотя файлы существовали
и не содержали ошибок (проверено `wp eval-file` — рендерят корректный HTML
в изоляции). Причина — `WP_Theme::get_block_patterns()` (WP ≥ 6.4) кэширует
список файлов в `patterns/` в **site transient**
(`wp_theme_files_patterns-<hash>`) на несколько часов, привязано к
`Version` в `style.css` темы. Первый скан (когда существовал только
`hero.php`) закэшировался, и WordPress не видел новые файлы, пока
transient не протух или не удалён вручную.

**Фикс:**
- В `.github/workflows/deploy.yml` добавлен шаг «Сбросить кэш файлов
  темы» — после каждого деплоя `wp transient delete --all` на сервере.
- В `.wp-env.json` добавлен `WP_DEVELOPMENT_MODE: "theme"` (отключает
  этот кэш для локальной разработки) — **но эта настройка не применяется
  сама по себе к уже запущенному контейнеру**, `wp-env start` не
  регенерирует `wp-config.php` на лету. Если снова столкнётесь с «паттерн
  не появляется» на локалке — сначала `wp transient delete --all`
  (быстро), при следующей возможности — `wp-env destroy && wp-env start`
  (пересоздаст `wp-config.php` с учётом `WP_DEVELOPMENT_MODE`, но сотрёт
  локальную БД — товары придётся сидить заново).

**Продолжение находки — первый фикс (transient) оказался недостаточным.**
После деплоя на staging с шагом «сбросить transient» новые секции
**всё равно не появились**, хотя файлы физически задеплоились
(проверено по `ls`/mtime по SSH) и transient гарантированно сбросился
(лог деплоя это подтвердил). Копнули глубже: сам
`_register_theme_block_patterns()` сканирует `patterns/` через
`scandir()`, а **и `wp-env` на Docker Desktop (Windows, bind-mount),
и, судя по всему, файловая система на этом shared-хостинге кэшируют
ЛИСТИНГ директории на уровне ОС дольше, чем в неё физически попадает
новый файл** — `file_exists()`/`stat()` на точный путь уже видят файл
сразу, а `scandir()` того же каталога — ещё нет (могло разрешиться и
само по себе через какое-то время, но зависеть от этого в проде нельзя).

**Окончательный фикс:** ушли от автосканирования директории вообще.
`functions.php` → `maderamas_register_patterns()` — регистрирует паттерны
по явному списку файлов (`add_action('init', ..., 5)`, до дефолтного
хука WordPress с приоритетом 10), метаданные читает `get_file_data()`,
контент — прямой `require()` по известному пути. Ни то, ни другое не
идёт через `scandir()`, так что кэш листинга директории эту логику
больше не касается. WordPress core увидит слаги уже
зарегистрированными на своём скане (приоритет 10) и просто пропустит
их — конфликта нет. **Новый паттерн — обязательно добавлять в список
файлов в этой функции**, иначе он не подключится ни при каких
обстоятельствах (это теперь единственный путь регистрации).

Оставленный шаг «сбросить transient» в `deploy.yml` не вреден (transient
всё ещё используется core-сканом как fallback-кэш), но для наших
паттернов он больше не обязателен.

## Локальная визуальная проверка не удалась (техническое ограничение)

Браузерный инструмент (Claude in Chrome) не может открыть
`http://localhost:8888/` — считает `localhost` «browser-internal» URL и
отказывается взаимодействовать. Визуальную проверку делаем только на
staging (доступен по `https://`, никаких ограничений). Локально —
только структурная проверка через `curl`/`wp eval` (наличие текста нужных
секций, отсутствие PHP fatal/parse ошибок в выводе).
