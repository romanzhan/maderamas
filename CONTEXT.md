## Хостинг: решение и почему

Коротко: **шаредхостинг Hostinger Premium, Сан-Паулу**, не VPS.

Ход рассуждения (сворачивать не стоит — пригодится, если придётся объяснять
заказчику или пересматривать):

- Изначально планировали VPS (Ubuntu 24.04 + CloudPanel) — казалось, что
  нужен root и SSH под rsync-деплой.
- Сравнили провайдеров с VPS: Hostinger (Сан-Паулу, известный, дёшево, но
  Аргентины у них нет), Vultr (Сан-Паулу, надёжно, руками больше), DonWeb
  (Аргентина, локальная задержка и factura, но контора меньше и скромнее
  инструментарий), AWS Local Zone Buenos Aires (низкая задержка, но дорого
  и избыточно для 8 товаров).
- Решающий факт: нынешний Tiendanube-магазин **уже** отдаётся из Бразилии
  (185.133.35.x зарегистрированы в BR) — переезд в Сан-Паулу ничего не
  ухудшает по сравнению с тем, что есть у покупателей сегодня. С Cloudflare
  впереди локация origin вообще перестаёт быть заметна.
- Потом проверили факт, который отменил решение о VPS: на шаред-планах
  Hostinger **есть SSH** (rsync тоже поддерживают официально) — но
  **только на Web Premium, Web Business и Cloud**, не на самом дешёвом
  тарифе. Для магазина на 8 товаров VPS оказался избыточен — купили
  Premium.
- Куплен план **Web Premium** (~13 000 ARS/мес на момент покупки — цена
  продления обычно заметно выше витринной, Hostinger обычно завлекает
  ценой за предоплату 24–48 месяцев).

Что это даёт и чего не даёт:
- Есть: SSH (порт **65002**, нестандартный — уже зашит в
  `.github/workflows/deploy.yml` через переменную `DEPLOY_PORT`), WP-CLI,
  выбор версии PHP в hPanel.
- Нет: root, тонкая настройка PHP-FPM/OPcache, обычно нет Redis. Для
  8 товаров не критично.
- На одном Premium/Business-плане можно держать **несколько сайтов** —
  `dev.maderamas.com.ar` и потом сам `maderamas.com.ar` можно на одной
  подписке, второй раз платить не придётся. Оговорка: сайты делят
  ресурсы и аккаунт.
- `proc_open`/`proc_close` в PHP отключены — часть wp-cli команд не
  работает (`wp --info`, автопроверка в `wp rewrite structure --hard`),
  но сам wp-cli и деплой это не блокирует, проверено на практике.

### Инциденты 2026-07-31: два падения боевого магазина при настройке DNS/домена

**Инцидент 1 (при делегировании NS на Hostinger).** hPanel
интерпретировал добавление домена `maderamas.com.ar` как «сайт» —
привязал WordPress-инсталляцию (до этого жившую в `dev.maderamas.com.ar`)
к апексу, переименовав папку. Когда NS переключились, Hostinger сам
сгенерировал дефолтную DNS-зону для этого «сайта» — apex/`www` стали
смотреть на инфраструктуру Hostinger вместо Tiendanube. Починили через
Hostinger API: удалили ошибочные записи, восстановили `@`/`www` →
Tiendanube. Для `dev` тогда сделали **parked domain** поверх апекса
(рабочий, но кривой промежуточный вариант — апекс физически «сайт»,
а нужный домен — алиас).

**Инцидент 2 (попытка сделать по-человечески, без костыля).** Чтобы
`dev.maderamas.com.ar` стал самим сайтом, а не parked domain, сделали
в hPanel **Change domain**: `maderamas.com.ar` → `dev.maderamas.com.ar`
(предварительно убрав parked domain, чтобы не было конфликта имён).
Файлы и база пережили операцию штатно (как и обещано в документации
Hostinger) — но **вся DNS-зона `maderamas.com.ar` при этом удалилась
целиком** (apex начал отдавать NXDOMAIN), потому что Hostinger, похоже,
привязывает жизненный цикл DNS-зоны к тому домену, который сейчас
числится доменом сайта, а не к домену как таковому. Магазин снова лёг.

Починили тем же способом: через API добавили `maderamas.com.ar` как
**parked domain** сайта `dev.maderamas.com.ar` (это пересоздало зону),
удалили автосгенерированные Hostinger-записи (A на их IP, самозамкнутый
CNAME `www`), прописали `@`/`www` → Tiendanube заново. Заодно поправили
`AuthUserFile` в `.htaccess` (путь снова переехал) и `DEPLOY_PATH` в
GitHub Secrets. `siteurl`/`home` не трогали — были уже правильные.

**Итоговая структура (то, что описано в разделе выше) — сайт в hPanel
привязан к `dev.maderamas.com.ar`, апекс — parked domain того же сайта**,
но с DNS, вручную указывающим на Tiendanube. По ощущениям хостинга это
всё ещё «apex как бы принадлежит хостинг-аккаунту» — то, чего хотелось
избежать, — но технически это единственная конфигурация в рамках
API/hPanel Hostinger, которая: (а) держит реальный сайт под `dev`,
(б) не роняет DNS-зону апекса, (в) не пересоздаёт её каждый раз при
правках. Разделить домены полностью (apex вообще не связан ни с каким
сайтом в аккаунте) через доступный API/hPanel не получилось — либо
сайт «занимает» домен целиком, либо домен не имеет DNS-зоны вовсе
(ошибка `[DNS:4009] Domain not found`).

**Урок на будущее:** любая операция в hPanel/API Hostinger, меняющая
привязку домена к сайту (`Add website`, `Change domain`), затрагивает
DNS-зону этого домена целиком — непредсказуемо и без явного
предупреждения. Перед такими операциями: **снять `curl`/`nslookup`
слепок текущих записей** (как в этом файле) и держать наготове рестор.
Hostinger API (`developers.hostinger.com`, токен в hPanel → Advanced →
API, см. `CREDENTIALS.local.md`) — быстрее и безопаснее ручных кликов
в hPanel для восстановления: снятие/починка каждый раз занимали минуты.

   `docs/content-guide.md`. Не блокирует, но эти цифры стоит сверить с
   заказчицей при случае.

Полная сводка по каждой позиции (цены, MLAU-артикулы, все found
discrepancies) — `docs/tasks/002-product-data-collection.md` и
`docs/content-guide.md`. Наполнение WooCommerce реальными товарами —
задача 008 (`docs/tasks/README.md`), можно брать в любой момент — данные
готовы. Вёрстка (задачи 003+) идёт параллельно уже сейчас.

### Решения по разработке (2026-08-18)

Заказчик поставил задачу срочно (черновой вариант для показа) и задал
рабочий режим — зафиксировано, чтобы не переспрашивать по новой:

- **Стек вёрстки — Tailwind CSS** вместо SCSS (прямое указание, качество
  вёрстки с ним выше). Готово: `tailwind.config.js` в корне читает
  палитру/шрифты из `theme.json` (не дублирует хардкодом), `postcss.config.js`,
  `.stylelintrc.json` (разрешает `@tailwind`/`@apply` для линтера), `style.scss`
  → `style.css` с `@tailwind` директивами. `npm run build`/`lint:css`/`lint:js`
  проверены — зелёные. `npm run lint:php` в этой машине не работает (нет
  `composer`/`php` локально) — не блокер, но проверять на деплое/CI.
- **Библиотеки, не самопись.** Карусели — Swiper (уже добавлен в
  `package.json`, тот же выбор, что и на референс-сайте). Иконки — SVG-
  библиотека (Lucide), без ручной generation каждой иконки.
  Подробности и обоснование — `docs/design-system.md`.
- **Шрифты бренда самохостятся.** Onest (заголовки) и Golos Text (текст) —
  вариативные `.woff2`, скачаны с Google Fonts и лежат в
  `wp-content/themes/maderamas/assets/fonts/` (только latin/latin-ext —
  сайт для покупателя испаноязычный), подключаются отдельным
  `wp_enqueue_style` в `functions.php`, в сборку Tailwind не идут.
- **Палитра/типографика в `theme.json` актуализированы** под утверждённый
  brand-гайд (было — черновые цвета-заглушки прошлой сессии). Полная
  таблица цветов с назначением (натуральная база / промо-only) —
  `docs/design-system.md`.
- **Товары — настоящие WooCommerce-продукты**, не зашиты в код. Иначе
  не будет работать корзина/чекаут — заказчик явно попросил делать
  правильно, а не быстрым хаком.
- **Разбивка на маленькие задачи.** Каждая страница/секция — отдельная
  задача с своим файлом в `docs/tasks/` (по одной задаче — один файл,
  принцип из альманаха vibe-coding, https://vibe.sukharev.dev/knowledge-base)
  и с чистым контекстным окном при выполнении — не тащим всю стройку
  в одну сессию. Список задач — `docs/tasks/README.md`.
- **Ревью — выборочное, не на каждый шаг.** Раз нужна скорость, глазами
  через браузер каждую секцию не гоняем. Исключение — **данные по
  товарам (цены, наличие, атрибуты)**: там обязательна сверка между
  источниками, ошибка в цене недопустима.
- **Аргентинский рынок.** Тексты — es-AR (не нейтральный/европейский
  испанский), с учётом лексики ниши (детская мебель, растущие стулья).

### Технический аудит референсов (сделан 2026-08-18)

- **`roststul.ru`** — это **не Битрикс** (гипотеза не подтвердилась),
  платформа **InSales** (SaaS, RU e-commerce). Код не наследуем (другой
  стек), но паттерны подтверждены и взяты за образец: карусель на первом
  экране на Swiper, карточка товара (фото + скидочный бейдж + цена/старая
  цена + CTA), промо-плитки. Полная сводка структуры страницы и
  используемых библиотек — `docs/design-system.md`.
- **Brand-гайд Madera Más** — распарсен по исходнику артефакта (не на
  глаз), вытащены точные hex-коды палитры, названия шрифтов (Onest,
  Golos Text — оба поддерживают кириллицу и латиницу, оба на Google
  Fonts) и **полная разметка утверждённой структуры главной** (раздел
  «04 Применения → Сайт» — промо-полоса, шапка, hero, категорийные
  плитки, сетка товаров, промо-баннер). Это и есть контракт на
  вёрстку главной — брать 1:1, с добавлением карусели в hero (отдельное
  требование заказчика поверх гайда). Всё — в `docs/design-system.md`.

### План

1. **Сбор и парсинг данных о товарах.** Источники: Tiendanube (фото,
   тексты, описания — парсим сами с боевого сайта), Mercado Libre (цены,
   описания — **обойти весь каталог продавца постранично**, не одну
   страницу), Word-документ заказчицы, альбом с фотосессией на Drive.
   Свести в единую рабочую таблицу **вне git** (сырые данные заказчика —
   не в репозиторий, только финально утверждённый контент уходит в
   WooCommerce на сервере).
2. **Сверка и ревью данных.** На пересечениях источников — разночтения
   в ценах, описаниях, атрибутах (`pa_color`, `pa_madera`) — фиксировать
   и уточнять у пользователя, а не гадать. Свести с заглушками в
   `docs/content-guide.md`.
3. **Вёрстка по задачам из `docs/tasks/`** — маленькими кусками (см.
   «Решения» выше): главная секция за секцией, каталог, карточка товара,
   корзина/чекаут (штатные WooCommerce-блоки/шаблоны, кастомизация
   только по месту, где расходится с гайдом).
4. **Наполнение WooCommerce.** Товары, атрибуты, фото (через WP-медиа —
   `uploads` не деплоится, см. `CLAUDE.md`), переводы через
   `Maderamas_Lang` (один пост на языки, без дублирования).
5. **Проверка перед показом заказчику.** `npm run lint`, обязательная
   сверка цен/наличия по товарам; общий визуальный проход — по
   возможности, не блокирует показ черновика.

Дальше заказчик подключается предметно — правки уже по месту.
