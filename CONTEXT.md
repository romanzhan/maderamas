## О проекте

Интернет-магазин детской мебели, рынок Аргентины. Переезжает с Tiendanube
(`maderamas.com.ar` сейчас резолвится на 185.133.35.13/14 — это Tiendanube,
хостится в Бразилии). **Tiendanube не отключать**, пока новый магазин не
пройдёт проверку реальными заказами — это единственный источник дохода на
время миграции.

Каталог маленький: **8 товаров**, известны из старого магазина. Атрибуты
(глобальные, WooCommerce) видны из фильтров Tiendanube:
- `pa_color` — реальные значения включают Blanco
- `pa_madera` — реальные значения включают Roble Americano, Nogal

⚠️ В `docs/content-guide.md` сейчас в таблице атрибутов **примеры-заглушки**
(`natural, blanco, miel` / `pino, paraíso, guatambú`) — их надо свести с
реальными значениями из Tiendanube перед наполнением каталога (Фаза 2).

Фазы (из `docs/plugins.md`, `docs/content-guide.md`):
1. Вёрстка/дизайн — **заблокирована**, ждём референсы от заказчика.
2. Структура каталога и контент.
3. —
4. Mercado Pago (боевые ключи).
5. SEO-плагин, кэш при необходимости.

## Хостинг: решение и почему

Коротко: **шаредхостинг Hostinger Premium, Сан-Паулу**, не VPS.

Ход рассуждения (сворачивать не стоит — пригодится, если придётся объяснять
заказчику или пересматривать):

- Изначально планировали VPS (Ubuntu 24.04 + CloudPanel) — казалось, что
  нужен root и SSH под rsync-деплой.
- Сравнили провайдеров с VPS: Hostinger (Сан-Паулу, известный, дёшево, но
  Аргентины у них нет), Vultr (Сан-Паулу, надёжно, руками больше), DonWeb
  (Аргентина, локальная задержка и factura, но контора меньше и скромнее
  инструментарий), AWS Local Zone Buenos Aires (низкая задержка, но дорого
  и избыточно для 8 товаров).
- Решающий факт: нынешний Tiendanube-магазин **уже** отдаётся из Бразилии
  (185.133.35.x зарегистрированы в BR) — переезд в Сан-Паулу ничего не
  ухудшает по сравнению с тем, что есть у покупателей сегодня. С Cloudflare
  впереди локация origin вообще перестаёт быть заметна.
- Потом проверили факт, который отменил решение о VPS: на шаред-планах
  Hostinger **есть SSH** (rsync тоже поддерживают официально) — но
  **только на Web Premium, Web Business и Cloud**, не на самом дешёвом
  тарифе. Для магазина на 8 товаров VPS оказался избыточен — купили
  Premium.
- Куплен план **Web Premium** (~13 000 ARS/мес на момент покупки — цена
  продления обычно заметно выше витринной, Hostinger обычно завлекает
  ценой за предоплату 24–48 месяцев).

Что это даёт и чего не даёт:
- Есть: SSH (порт **65002**, нестандартный — уже зашит в
  `.github/workflows/deploy.yml` через переменную `DEPLOY_PORT`), WP-CLI,
  выбор версии PHP в hPanel.
- Нет: root, тонкая настройка PHP-FPM/OPcache, обычно нет Redis. Для
  8 товаров не критично.
- На одном Premium/Business-плане можно держать **несколько сайтов** —
  `dev.maderamas.com.ar` и потом сам `maderamas.com.ar` можно на одной
  подписке, второй раз платить не придётся. Оговорка: сайты делят
  ресурсы и аккаунт.
- `proc_open`/`proc_close` в PHP отключены — часть wp-cli команд не
  работает (`wp --info`, автопроверка в `wp rewrite structure --hard`),
  но сам wp-cli и деплой это не блокирует, проверено на практике.

Поднят и работает: **https://aqua-mantis-161501.hostingersite.com/**
(временный домен Hostinger, аккаунт `u489565363`, IP `185.211.7.151`,
SSH-порт `65002`).

Сделано:

  совпала с `.wp-env.json` — переустановки не потребовалось).
- WooCommerce 10.9.4 + Mercado Pago 8.9.0 — версии как в
  `.wp-env.json`/`docs/plugins.md`.
- `wp-config.php`: `WP_ENVIRONMENT_TYPE=staging`, `DISALLOW_FILE_EDIT=true`.
  `DISALLOW_FILE_MODS` сознательно **не** ставили — может помешать
  собственным автообновлениям хостинг-плагинов Hostinger.
- Аргентинские настройки WooCommerce (ARS, AR:C, `/productos/` и т.д.).
- Тема `maderamas` задеплоена и активирована, дефолтные темы удалены.
- `mu-plugins` Hostinger (`hostinger-auto-updates.php`,
  `hostinger-preview-domain.php`) не тронуты — деплой синхронизирует
  в `mu-plugins` только файлы с префиксом `maderamas*` (см. #4 ниже).
- Автодеплой работает: push в `main` → GitHub Actions → rsync на
  staging. Секреты/переменные в GitHub (environment `staging`):
  `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_PATH`, `DEPLOY_SSH_KEY`,
  `DEPLOY_PORT=65002`, `DEPLOY_ENABLED=true`.
- `noindex` работает (проверено: `<meta name='robots' content='noindex, nofollow' />`).
- Админка на русском лично для администратора (`user_meta.locale=ru_RU`),
  сайт для покупателей остаётся `es_AR`.
- **Basic Auth настроен и работает** (origin проверен: без пароля — 401,
  с паролем — 200; `admin-ajax.php`/`wp-cron.php` доступны без пароля).
  Логин `maderamas`, пароль — см. переписку (не в git, не в этом файле).
  Реализация и грабли — в `docs/deploy.md`. Коротко: у Hostinger перед
  origin стоит свой CDN (`hcdn`), который кэшировал HTML на неделю
  из-за дефолтного `ExpiresDefault` в `.htaccess` — убрали, `litespeed-cache`
  выключили на время действия пароля (иначе CDN снова закэширует мимо
  Auth), права на `.htpasswd` — обязательно `644` (LiteSpeed-воркер
  читает файл не от имени владельца).
  ⚠️ **Не до конца закрыто**: главная страница на момент проверки ещё
  отдавалась из старого CDN-кэша (закэширована ДО того, как поставили
  пароль) — нужен ручной Purge в hPanel, это ЕДИНСТВЕННЫЙ оставшийся шаг
  для полной защиты (см. открытые задачи, п.1).
- **WP-автообновления уже отключены** штатно — мu-plugin Hostinger
  (`hostinger-auto-updates.php`) сам ставит
  `automatic_updater_disabled=true` и `auto_update_theme/plugin=false`.
  Отдельный переключатель в hPanel (см. п.3 открытых задач) — это другой,
  серверный механизм Hostinger вне WP, его надо проверить отдельно.

Баги, найденные и починенные по пути (см. PR #4, #5+#6):
- rsync `--delete` по всей `mu-plugins` чуть не затёр файлы Hostinger —
  пофикшено `--include='maderamas*' --exclude='*'`.
- Секрет `DEPLOY_PATH` ломался при установке из Git Bash на Windows
  (MSYS сам конвертирует `/home/...` в путь Windows) — чинится
  `MSYS_NO_PATHCONV=1 gh secret set ...`. `--old-args` для rsync
  оказался не нужен, это была неверная гипотеза (см. #5 → revert #6).
- Basic Auth через `<Files>`-исключение для `admin-ajax.php`/`wp-cron.php`
  не сработал (похоже на `AuthMerging`, сливающий правила вместо
  переопределения) — пофикшено одним `<FilesMatch>` с отрицательным regex.
  `.htpasswd` с правами `640` не читался LiteSpeed-воркером (другой
  пользователь) — фикс `chmod 644`.

## Открытые задачи — что осталось сделать руками (доступ только у вас)

1. **Почистить CDN-кэш Hostinger.** hPanel → Advanced → Cache Manager →
   **Purge All**. Без этого шага главная страница staging всё ещё может
   отдаваться без пароля из старого кэша (закэширован до Basic Auth).
   Единственное, что реально осталось для полной защиты стенда.
2. **DNS.** `dev.maderamas.com.ar` пока никуда не указывает (проверено
   `nslookup` 2026-07-30 — NXDOMAIN). В Route 53 добавить A-запись
   `dev.maderamas.com.ar` → `185.211.7.151`. Апекс и `www` не трогать —
   там живой Tiendanube-магазин. (Правильная зона — `maderamas.com.ar`,
   не `maderamas.co.ar`, была путаница ранее.)
   После DNS — ещё нужно **привязать домен в hPanel** (Websites → Add
   website / подключить существующий домен к этому хостингу), иначе
   даже с правильным DNS сервер не будет знать, что на этот домен
   отвечает именно этот сайт. И проверить, что SSL (Let's Encrypt)
   выпустился на новый домен — обычно автоматически, но стоит
   перепроверить в hPanel после переключения.
3. **Проверить автообновления в hPanel.** WordPress → Security →
   «Don't update» (или аналогичный тумблер). На уровне WP они уже
   отключены (см. выше), это доп. слой на стороне Hostinger — не
   проверено, включён ли уже.
4. **Референсы дизайна.** Не присланы. Фаза 1 (вёрстка) без них не
   двигается.
5. **Наполнение каталога.** 8 товаров и атрибуты известны из старого
   Tiendanube, но не сведены с заглушками в `docs/content-guide.md`.
6. Прод (`www.maderamas.com.ar`) не трогаем, пока staging не обкатан.
